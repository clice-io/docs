符号索引 ​

背景 ​

语言服务器的很多功能需要跨文件工作。用户在一个文件中触发“跳转到定义”，目标可能在项目中的任意另一个文件；“查找引用”需要扫描项目中可能提及该符号的所有文件；调用层次和类型层次涉及跨多个文件的符号关系链。为支持这些功能，语言服务器必须维护一个覆盖整个项目的符号索引，记录每个符号出现在哪些文件中以及它们之间的语义关系（定义、引用、调用、继承等）。

C++ 让索引的构建和维护变得特别困难。

第一层困难是头文件的编译上下文问题。C++ 的 #include 是文本替换——头文件的内容在编译时被逐字插入到包含它的源文件中。这意味着同一个头文件在不同的编译上下文中可能产生完全不同的符号：

cpp
// crypto.h
#ifdef USE_OPENSSL
    using TLSContext = OpenSSLContext;
#else
    using TLSContext = BoringSSLContext;
#endif

当 crypto.h 被一个定义了 USE_OPENSSL 的源文件包含时，TLSContext 是 OpenSSLContext；被另一个源文件包含时，它是 BoringSSLContext。条件编译是最直观的例子，但 include 顺序和模板实例化也可能导致头文件在不同上下文下产生不同的符号关系。如果索引只记录一个上下文的结果，用户切换上下文后就会看到错误的跳转目标或不完整的引用列表。

第二个层面是规模。一个中等规模的 C++ 项目（数千个源文件）编译后产生数十万个符号；大型项目（LLVM、Chromium）达到百万量级。索引系统必须在这个规模下保持合理的内存占用、构建时间和查询延迟。

clangd 在这两个层面的处理都有不足。在编译上下文方面，clangd 的后台索引对每个头文件只保留最后一次编译的结果——最后编译的源文件会覆盖先前的索引数据。如果某个符号引用只存在于某个特定的编译上下文，而该上下文不是最后被索引的，这条引用就丢失了。

在跨文件查找方面，clangd 的后台索引把符号信息存储在与符号声明所在文件对应的索引分片中。这种以声明文件为中心的存储模式导致引用计数无法在文件之间正确累加（clangd #23）。用户也经常遇到“查找引用”结果不完整的情况——某些引用直到手动打开相关文件后才出现，此时动态索引才补上缺失的数据（clangd #516、#802）。此外，编译命令变化时，clangd 的过期检测不会触发重新索引（clangd #199），导致索引数据长时间与实际编译状态不一致。

clice 的索引系统针对这些问题重新设计：将全局符号目录与按文件分片的关系数据分离；通过内容相同的变体去重合并同一文件的不同编译上下文；把所有索引 blob 存储在单个嵌入式数据库中，提供零拷贝的按需访问；并为打开文件叠加实时数据，保证编辑过程中查询结果的时效性。

设计 ​

符号标识 ​

索引系统需要一种跨文件、跨翻译单元标识同一个符号的方式。clice 使用 SymbolHash（64 位整数）作为每个符号的唯一标识。

SymbolHash 基于 Clang 的 USR（Unified Symbol Resolution）生成。USR 是符号身份的规范字符串表示，编码了符号的完全限定名：命名空间、类名、函数签名、模板参数等。例如，std::vector<int>::push_back 和 std::vector<double>::push_back 产生不同的 USR。SymbolHash 是对 USR 字符串计算的哈希值。

SymbolHash 有两个关键特性。第一，跨文件一致：同一个符号无论在哪个文件中出现，SymbolHash 始终相同。文件 A 中的 std::string 和文件 B 中的 std::string 拥有相同的哈希，通过它可以关联所有的定义和引用——这是跨文件导航的基础。第二，紧凑性：64 位整数比可变长度的 USR 字符串更适合作为哈希表的键和序列化存储。

符号出现与符号关系 ​

索引存储两种核心数据：符号出现（Occurrence）和符号关系（Relation）。

Occurrence 记录一个符号在源码位置的出现，只包含源码范围和目标符号的 SymbolHash。它回答的问题是“光标位置下是什么符号”。

Relation 记录更丰富的语义信息，包含三个要素：关系类型（RelationKind）、源码位置、以及目标符号。关系类型涵盖常见的符号间语义：

  • 定义与声明（Definition、Declaration）
  • 引用（Reference、WeakReference）
  • 继承（Base、Derived）
  • 调用（Caller、Callee）
  • 类型关系（Interface、Implementation、TypeDefinition）
  • 构造与析构（Constructor、Destructor）

两者分开存储是因为查询模式不同。Occurrence 按位置索引——给定一个字节偏移量，用二分查找快速定位光标下的符号。Relation 按 SymbolHash 索引——给定一个符号，查找它的所有定义、引用和调用关系。这两种查询对数据排序的要求相互矛盾，分开存储使两种查询都能高效执行。

索引层次 ​

clice 的索引分为多个层次，每层有不同的生命周期和职责：

TUIndex        Raw artifact from one compilation, discarded after merging
    ↓ merge
ProjectIndex   Global directory: external symbols + which TUs contributed which files
Shard          Per-file variant storage (exact positions and relations), loaded on demand
    ↑ overlay
Live rows      The open buffer's latest compile results, owned by its published projection

TUIndex 是编译一个翻译单元产生的原始索引数据，从编译期间构建的统一语义映射投影而来。由于一次编译涉及主文件和所有被包含的头文件，TUIndex 内部为每个文件维护独立的行集合。它还携带一份符号表（哈希到名称和种类）和本次编译的 include 图。TUIndex 是临时数据，合并到持久索引后即被丢弃。

ProjectIndex 是全局目录。它有两个职责：为外部可见符号维护全局符号表（SymbolHash → 名称、种类、引用文件位图，使用 Roaring Bitmaps 压缩），以及记录哪些翻译单元贡献了哪些文件（这是变体存活和翻译单元消失时进行对账的基础）。它不存储符号的精确位置——它告诉你符号存在于哪些文件中，具体位置在对应的分片里。这种分离使 ProjectIndex 保持紧凑，可以常驻内存。

Shard 是按文件存储的单元，也是实际响应查询的层。每个以不同方式预处理该文件的编译上下文贡献一个变体——一个自包含、规范编码的文件行 blob。文件本地名称（内部链接、函数局部变量、匿名命名空间成员）存放在 shard 自己的本地名称表中；只有外部名称进入 ProjectIndex。Shards 按需加载——大多数在会话中从未被访问。

打开文件的 Live rows 来自其最近一次内存编译，归文档已发布的投影所有。它们从不写入全局状态——只在查询时作为叠加层，因此结果反映用户实际编辑的缓冲区内容。

符号表分层 ​

符号元数据（名称、种类）按层次查找：先查打开文件的实时数据，再查 ProjectIndex 全局表中外部名称，最后查 shard 本地名称表中的文件本地名称。存储遵循可见性——没有任何其他文件能引用的符号不会污染全局表。

实现 ​

索引构建 ​

TUIndex 的构建是对统一语义映射的投影：每次编译遍历一次 AST，记录所有感兴趣的节点，索引投影按文件输出 Occurrence 和 Relation 行。投影之后，每个文件的行被规范化——去重并排序（出现按位置排序以支持二分查找，关系按类型和位置排序以支持过滤）——从而保证编码后的 blob 是确定性的。

构建期间，主文件的记录与头文件的记录分开保存。这样可以在合并时区别对待——主文件作为翻译单元自身的贡献合并，头文件则作为上下文变体合并。

基于内容身份的变体去重 ​

shard 面对的核心问题是：同一个头文件被 N 个源文件包含，产生 N 份记录集合。如果每份都完整存储，存储量会随翻译单元数量线性增长。但实际上，绝大多数头文件在不同编译上下文下产生的索引数据完全相同。只有上面 crypto.h 这样受条件编译影响的头文件，才会在不同上下文下产生不同内容。

clice 的解法是让编码后的字节本身成为身份标识。每个变体都以规范化、确定性的方式编码——同样的记录产生同样的字节——其身份（RowsHash）是这些字节的 xxh3 哈希。当一次新的编译贡献一个变体时：

  1. 将该文件的记录编码成规范 blob 并对其计算哈希
  2. 如果 shard 中已存在具有此身份的变体，合并就只是记账——记录贡献的 TU，不解码、不重写任何内容
  3. 如果是新身份，则将该 blob 作为新变体加入

实践中，绝大多数合并都只走记账路径，这正是全项目索引成本低的原因：重新索引一个未变化的头文件完全不会触碰 shard 的任何字节。

哪些变体是活跃的，由贡献记录推导出的变体掩码决定：当一个翻译单元被移除或重新索引后，它不再担保的变体会从活跃集合中退出，并在查询中被过滤掉。

零拷贝存储 ​

所有索引 blob——shard、manifest、序列化的 ProjectIndex——都存放在一个嵌入式 LMDB 数据库中。Blob 的编码是规范且自描述的；加载时先验证一次，然后直接作为内存映射的零拷贝视图使用。读取路径上没有反序列化成结构体的步骤。

启动时只加载 ProjectIndex 和每个 TU 的 manifest（紧凑）。Shard 按需打开，大多数 shard 在一次会话中从未被访问。

每 TU 上下文 ​

上下文信息——一个翻译单元看到了哪些文件、经由哪棵 include 树——按翻译单元存储一份在其 manifest 中，而不是复制到每个 shard。Shard 只知道变体；manifest 知道哪个 TU 为哪个文件贡献了哪个变体。过期与对账决策（TU 从 CDB 中消失、命令变化、依赖变化）由 manifest 和贡献记录驱动。

查询流程 ​

以“查找引用”为例说明完整的跨文件查询流程：

  1. 在当前文件中，用光标的字节偏移量二分查找 Occurrence 记录，得到光标下符号的 SymbolHash
  2. 在 ProjectIndex 中查找该 SymbolHash 的引用文件位图，得到所有包含该符号的文件
  3. 对列表中的每个文件分别查询：
    • 如果文件已打开，由其活跃记录（来自最近的内存编译结果）回答，前提是它们对缓冲区是最新的
    • 对于打开的文件，只有当缓冲区内容与 shard 索引的内容逐字节一致时，才会查询磁盘数据——被编辑过的缓冲区绝不提供过期的磁盘位置
    • 未打开的文件由其 shard 的活跃变体回答
  4. 汇总跨文件找到的所有 Relation 记录（按目标 RelationKind 过滤），转换为 LSP 位置后返回给客户端

对于 preamble 被编译进 PCH 的打开文件，配对的 preamble 状态 blob（见下文）提供被 PCH 吞掉的那些记录。

将偏移量转换为 LSP 位置需要文件的行首信息。Shard 存储行表（以及足够的内容）用于此转换，因此即使文件未打开也能完成。

过期检测 ​

过期检测判断一个文件是否需要重新索引。每个索引产物记录其输入的身份和观测到的内容版本；校验交给 master 的共享文件表，它执行与各处相同的两层检查——先走 (size, mtime) stat 快速路径，再做内容哈希确认并修复 stamp（见 Incremental Compilation）。仅当输入内容实际变化时才触发重新索引；命令变化通过 manifest 中记录的 entry 身份哈希单独捕获。

后台索引调度 ​

后台索引调度需要在索引及时性和对用户交互的干扰之间取得平衡。索引模块采用以下策略：

  • 空闲延迟队列：需要索引的文件先加入队列，只有编辑器空闲了一段可配置的时间后才开始处理。这避免了快速编辑期间触发索引任务。
  • 前台感知的预算：用户活跃时，后台索引运行被限制在 worker 池的一部分；前台空闲后扩展到全部容量。内存压力会进一步压缩可用额度（见 Multi-process Architecture）。
  • 结果合并与持久化：每个索引任务在无状态子进程中编译一个文件并构建 TUIndex。结果序列化后送回主进程，由主进程合并进项目索引和 shards。被修改的 blob 以批量事务提交到数据库，下次启动时可以直接加载。

FAQ ​

  • 为什么把 ProjectIndex 和 shards 分开，而不是用一个统一索引？

    如果位置信息也存入 ProjectIndex，它的体积会急剧膨胀，无法常驻内存。如果没有 ProjectIndex，每次跨文件查询都需要遍历所有 shards 来定位包含该符号的文件——在一个有数万文件的项目里，加载这么多 shards 是不可接受的。ProjectIndex 充当轻量目录层，先把搜索范围缩小到少数几个具体文件，再到对应 shards 中精确查找。

  • 为什么打开文件的索引不写入全局状态？

    用户正在编辑的缓冲区内容可能是不完整的、有语法错误的代码。如果这种临时状态被写入全局索引，会污染其他文件的查询结果。例如，正在编辑的头文件中某个符号定义暂时消失，会影响所有引用该符号的文件的 find-references 结果。全局索引只接受保存到磁盘的稳定状态，通过后台索引从磁盘文件构建。

  • 内容身份去重存在哈希冲突风险吗？

    Variant 的身份是编码后 blob 的 64 位哈希，冲突概率极低，但并非密码学上不可能。冲突会让两个真正不同的 Variant 共用一份存储副本——对某个上下文返回错误的行——但不会破坏数据结构或导致服务器崩溃。这个权衡（在热合并路径上使用便宜得多的哈希）是有意为之。

  • 为什么用自定义规范化编码，而不是通用序列化框架？

    两个原因。第一，零拷贝：blob 只校验一次，之后直接从映射内存服务查询，通用框架对此支持程度不一。第二，也是更深层的原因——字节身份就是合并货币：因为编码是行的严格确定性函数，“内容相同”和“字节相同”完全一致，去重就变成哈希比较而不是结构 diff。输出可能变化的框架（字段顺序、填充、带版本的 wire format）会破坏这种等价性。

  • 为什么把 Occurrence 和 Relation 分开存储？

    Occurrence 按位置索引——给定偏移量，二分查找定位光标下的符号，这要求数据按位置排序。Relation 按 SymbolHash 索引——给定符号，查找它的所有关系，这要求数据按符号分组。把两者合并进一个数据结构，必然在其中至少一种查询模式上损失效率。

  • 为什么跨文件查询在主进程而非子进程中完成？

    clice 采用多进程架构，每个打开的文件在自己的有状态子进程中编译。跨文件查询（如查找引用）需要把所有打开文件的实时行与持久索引合并。如果这些实时行分散在不同的子进程中，每次查询都需要与多个 worker 进行跨进程通信，然后再聚合结果——延迟和复杂度都无法接受。相反，子进程完成编译后把索引行送回主进程，由主进程统一执行查询——它能同时看到所有打开文件的实时行以及 ProjectIndex 和 shards，在单个进程内完成完整查询流程。

    这个设计还有一层语义上的考虑：打开文件的查询结果应该反映编辑器的缓冲区状态，而不是磁盘状态。即使磁盘上的文件被外部工具修改过，只要编辑器没有发送 didChange 通知，查询结果就应基于编辑器持有的版本。把实时行集中到主进程管理，使这个语义不变量更容易维护。

  • 为什么索引用嵌入式数据库存储，而 PCH/PCM 用普通文件？

    它们的数据形态截然相反。索引 blob 数量多（每个项目文件一个 shard）、单个体积小，且在后台索引期间成批写入——这正是单个 LMDB 数据库占优的场景：批量原子提交、大规模下没有逐文件的目录项压力，以及内存映射读取保留零拷贝路径。PCH 和 PCM 文件恰好相反：数量少、体积大（数百 MB）、由 Clang 本身直接内存映射，生命周期简单——创建、读取、淘汰；文件系统加上产物存储的原子重命名提交就能处理得很好，而且 Clang 本来也无法从数据库里消费它们。在数据库无法安全运行的文件系统上（如网络挂载），索引持久化会被禁用，而不是降级。

已知局限 ​

  • 内部链接符号的跨 TU 查询。 文件局部名称存储在 shard 的 local-name 表中，但跨文件关系查询路径目前只能通过外部符号目录到达磁盘——因此对 static 函数执行"查找引用"只会返回实时覆盖层能看到的结果。存储分层已就位；局部符号的查询路径还没就位。

  • 模糊符号搜索。当前的工作区符号搜索（workspace/symbol）是简单的子串匹配，对 ProjectIndex 中的所有符号做线性扫描。这在大型项目中不够用，也不支持模糊匹配。

    C++ 符号名有结构：getSymbolHash 是 camelCase，get_symbol_hash 是 snake_case，std::vector<int>::push_back 带命名空间限定。用户搜索时通常只输入缩写或片段（如 symhash、gSH、vec_pb），期望匹配到完整符号名。子串匹配无法处理这类查询。

    改进方向是为符号名建立专门的搜索索引。需要一个 tokenizer 按命名约定拆分符号名（getSymbolHash → [get, Symbol, Hash]，push_back → [push, back]），然后基于 token 建立倒排索引。例如，可以用 trigram（三字符组）作为索引键，查询时取 trigram 交集得到候选集，再做精确评分。clangd 的 Dex 索引采用了这种 trigram posting list 方案，是一个可参考的实现。另一个方向是引入成熟的全文搜索库，不过需要评估引入外部依赖的代价。

  • PCH 导致的索引分裂（已解决）。使用 PCH 优化时，一个文件的编译被分成两个阶段：先把 preamble 编译成 PCH，再用 PCH 编译文件的其余部分。PCH 吞掉了 bound 之前的一切——主文件的编译既看不到头文件的内容，也看不到 preamble 区自身的指令；而且打开缓冲区的 preamble 可能描述一个任何磁盘翻译单元都未曾以之索引过的编译上下文。

    现在的方案是为每个 PCH 配对一个 preamble 状态 blob，由同一次 worker 构建在刚解析完的 preamble AST 仍在内存时产出（这是唯一无需完整反序列化 PCH 就能获得其索引的时机）。blob 携带 preamble 的完整符号索引——覆盖的每个头文件加上主文件的 preamble 区——以及每文件的内容与行表（用于位置换算）、document links、非活跃区域和未闭合条件栈。它与 PCH 一同存储、一同命中、一同淘汰，以内存映射 FlatBuffer 形式打开，查询无需反序列化。打开文件把这些 blob 作为 overlay 叠加到索引查询上：集合查询与磁盘分片取并集（相同行按位置坍缩），单答案查询优先 overlay，缓冲区 preamble 区的游标经 blob 的主文件条目解析。这使得后台索引尚未（或无法）覆盖其翻译单元的打开文件仍能正常导航，查询结果也忠实于未保存的 preamble 编辑。
