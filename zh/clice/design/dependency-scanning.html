依赖扫描 ​

背景 ​

C++ language server 需要知道文件之间的 include 关系。这个需求来自几个方面：

头文件的编译上下文：头文件不在编译数据库（CDB）中，因此 language server 必须为每个头文件选择一个宿主源文件，以获取编译命令。这需要知道“哪些源文件包含这个头文件”——即反向 include 关系。没有这个信息，用户打开头文件时无法获得正确的诊断、补全或导航功能。

模块依赖解析：编译 C++20 模块需要知道模块之间的依赖关系。模块名到文件的映射以及模块之间的导入关系必须通过扫描文件内容来发现。

优先级调度：后台索引需要确定文件的索引顺序。与用户当前打开的文件存在 include 关系的文件应该优先索引。include 图可以用来跟踪这种相关性。

问题在于，精确确定 include 关系需要运行完整的 C 预处理器——展开所有宏并求值所有条件编译指令。对于大型 C++ 项目（数万个文件），在启动时对每个文件运行预处理器需要数分钟，这是不可接受的。

clangd 的做法是在后台索引期间逐步构建 include 图——每次编译一个文件时，记录它的 include 关系。这意味着在后台索引完成之前（可能需要数十分钟），include 图是不完整的。在此期间打开头文件的用户可能找不到正确的宿主源文件，导致诊断错误。在 clangd 社区中，用户多次报告启动后很长时间内头文件显示错误的诊断，需要等待后台索引完成后才正确。

clice 通过专门构建的快速依赖扫描器解决这个问题——用精度换取足够好的结果，能够在启动的几秒内扫描数万个文件。

设计 ​

核心思想 ​

依赖扫描的核心权衡是用精度换取速度。完整的预处理器可以精确确定哪些 include 是活跃的、哪些被条件编译排除，但它有一个根本的性能问题：同一个头文件在不同的源文件上下文中可能产生不同的展开结果，因此每个 (源文件, 头文件) 组合都必须独立预处理——结果无法共享。快速扫描器放弃预处理，使扫描结果独立于包含上下文——每个文件只需扫描一次，结果在所有上下文中共享。代价是所有条件分支中的 include 都被视为活跃，产生所有可能 include 关系的超集。虽然这个超集比实际的 include 关系大，但它对依赖扫描的主要用例是安全的：

  • 查找宿主源文件时，超集可能产生更多候选宿主，但不会遗漏正确的宿主。
  • 判断文件相关性时，超集可能将一些不相关的文件视为相关，但不会错过真正相关的文件。

为什么这么快 ​

快速扫描器的速度来自一个根本的设计选择和几个关键优化：

根本优势：跨上下文结果共享

这是快速扫描器比完整预处理快几个数量级的根本原因。在完整预处理下，当不同的源文件包含同一个头文件时，前面的 #define 和 #include 不同，因此预处理结果可能完全不同。这意味着每个 (源文件, 头文件) 组合都必须独立预处理——工作量是 O(源文件数量 × 平均头文件深度)。对于有数万个源文件的大型项目，每个源文件平均包含数百个头文件，这相当于数百万次预处理操作。

快速扫描器放弃预处理，因此扫描结果与包含上下文无关——同一个头文件无论被哪个源文件包含，都会产生相同的 #include 列表。这意味着每个头文件只需要扫描一次，结果在所有源文件之间共享。工作量降为 O(唯一文件数)——通常只是几千到几万个文件，而不是数百万次操作。

轻量级词法扫描

扫描器使用 Clang 的依赖指令扫描器（scanSourceForDependencyDirectives），它只识别以 # 开头的预处理指令行，不进行宏展开、不求值条件表达式、不展开 include。扫描每个文件只需要微秒级时间。

扫描结果是原始 include 名称（例如 "foo.h" 或 <vector>），需要后续的路径解析阶段将它们映射为实际文件路径。

对于条件编译内部的 include，扫描器通过跟踪 #if/#ifdef/#ifndef 的嵌套深度来标记它们：在深度大于 0 处遇到的 include 被标记为“条件性的”。虽然这个标记不知道条件表达式的具体求值结果，但它提供了有用的元数据。

分离的路径解析阶段

将 include 名称映射为实际文件路径是一个独立阶段。解析器使用目录列表缓存——它预读搜索路径中每个目录的文件列表，然后通过内存中的字符串集合检查文件是否存在，避免大量 stat 系统调用。

尖括号 include（例如 <vector>）的解析结果可以跨文件缓存——在相同的编译配置下，相同的头文件名总是解析到相同的路径。双引号 include 依赖于包含者所在目录，无法跨文件缓存，但每个文件通常只有很少的双引号 include。

波前 BFS 发现

扫描不是一次性处理所有文件，而是按波次展开：

  • Wave 0：扫描编译数据库中的所有源文件（并行 I/O + 词法扫描）
  • 路径解析：将发现的 include 名称映射为文件路径，识别出新发现的头文件
  • Wave 1：扫描新发现的头文件，发现它们包含的 include……
  • 重复直到没有新文件被发现

一项关键优化：当前波次执行路径解析（串行）时，下一波次的文件已经可以开始预取和扫描（并行）。这种流水线式重叠掩盖了大部分 I/O 延迟。

DependencyGraph 存储结构 ​

DependencyGraph 存储文件之间的 include 关系，支持正向和反向查询：

正向 include：给定文件和编译配置，返回它直接包含的所有文件。每条边记录它是否是条件 include（通过位标志区分）。同一个文件在不同编译配置下可能有不同的 include 集合（因为搜索路径不同），因此键是 (文件, 配置) 对。

反向 include：给定文件，返回所有直接包含它的文件。这是一个在所有正向 include 建立后批量构建的反向索引。它用于“查找宿主源文件”——从目标头文件出发，沿反向边向上 BFS，直到找到有 CDB 条目的源文件。

模块映射：从模块名到模块接口单元文件路径的映射，用于 C++20 模块依赖解析。只有接口单元（export module）会被注册到映射中。一个模块名可能对应多个路径（当同一个模块在不同编译配置中被发现时）。

处理条件 include ​

扫描器不求值条件表达式，而是使用嵌套深度跟踪将 include 标记为“条件性的”或“无条件的”：

cpp
#include <vector>           // unconditional (depth 0)
#ifdef USE_BOOST
#include <boost/any.hpp>    // conditional (depth 1)
#ifdef BOOST_HAS_X
#include <boost/x.hpp>      // conditional (depth 2)
#endif
#endif
#include <string>           // unconditional (depth 0)

当查询一个文件在所有配置下的 include 并集时，如果同一个头文件在某个配置下是无条件的，在另一个配置下是条件性的，无条件优先——这反映了“至少在某个配置下，它一定会被包含”的语义。

处理模块声明 ​

C++20 模块声明（export module foo;、module foo:bar;）通常出现在文件顶部，快速扫描器可以直接识别它们。然而，如果模块声明出现在条件编译块（#ifdef）内部，快速扫描器无法确定哪个声明实际生效。

在这种情况下，扫描器会设置 need_preprocess 标志，触发精确回退——只对文件头部（到模块声明为止）运行预处理器，求值条件表达式以确定实际的模块名。这个回退只影响极少数文件（绝大多数模块声明位于顶层），不会影响整体扫描速度。

缓存与增量更新 ​

扫描结果在多个层级进行缓存：

  • 扫描结果缓存：每个文件的扫描结果（include 列表、模块声明）按 master 的文件表中的文件标识和内容版本记录，只要内容版本仍然匹配，就会在多次重扫中复用——保存后的重扫只重新读取内容实际发生变化的文件。缓存只存在于内存中；服务器重启后从零开始扫描。
  • 目录列表缓存：搜索路径中每个目录的文件列表缓存在内存中，在初始扫描期间通过并发的 readdir 任务填充。
  • include 解析缓存：尖括号 include 的解析结果按（配置，头文件名）缓存，包括解析失败的负缓存。

与宿主源文件查找的协作 ​

依赖扫描的核心用途之一是为头文件查找宿主源文件。过程如下：

  1. 从目标头文件出发，沿反向 include 索引向上遍历
  2. 找到所有传递包含目标头文件的根文件（没有被任何其他文件包含的文件）
  3. 筛选出在 CDB 中有编译命令的源文件作为候选宿主
  4. 选择第一个具有有效 include 链的候选宿主作为默认宿主

include 链查找使用 BFS，以保证找到最短路径。编译上下文系统随后使用这条 include 链合成头文件的编译环境。

精确扫描与后台索引作为补充 ​

快速扫描在启动阶段提供近似结果。随着服务器运行，后台索引系统逐步编译项目中的每个翻译单元，在编译过程中获得精确的 include 关系（完整预处理，求值所有宏和条件编译）。这些精确的 include 关系记录在索引数据（TUIndex/MergedIndex）中。注意，后台索引目前不会更新启动时构建的 DependencyGraph——快速扫描的 include 图在整个服务器生命周期内仍用于宿主源文件查找和文件依赖查询。

此外，系统提供精确扫描模式（scan_precise）——对需要准确依赖信息的特定场景运行完整的 Clang 预处理器，例如模块编译期间的惰性依赖解析（通过 CompileGraph 的 resolve_fn）。精确扫描结果是已解析的文件路径（而非原始 include 名称），准确反映特定编译配置下的实际 include 关系。

快速扫描和后台索引是互补的：快速扫描保证启动后数秒内就能获得可用的 include 图（因此用户可以立即获得头文件支持），而后台索引在随后的几分钟内逐步补充精确信息。两者不是替代关系——即使后台索引完成之后，快速扫描结果仍用于初始文件发现和构建初始依赖图。

设计决策与权衡 ​

为什么用超集而不是精确结果？ 精确结果需要运行预处理器，对上万个文件需要数分钟。超集在数秒内完成，并且对宿主查找和关联性判断是安全的——多找到几个候选宿主远比遗漏正确的宿主好。

为什么不完全依赖后台索引来构建精确的 include 图？ clangd 完全依赖后台索引来构建 include 关系，但后台索引可能需要数十分钟才能完成。在此期间，头文件体验是不完整的——用户打开头文件会看到错误的诊断，需要很长时间才能自行纠正。clice 使用快速扫描保证启动后数秒内就有可用的 include 图，随后由后台索引逐步补充精确信息。两者结合既保证了即时可用性，也保证了最终的精确性。

为什么逐波展开而不是一次性扫描所有文件？ 系统事先不知道哪些头文件需要扫描——它们不在 CDB 中，只能通过解析源文件的 include 来发现。波前展开是惰性发现的自然模式，而流水线重叠最大化并行度。

为什么条件 include 标记有用？ 虽然具体的条件求值结果未知，但区分“一定会被包含”和“可能被包含”能为宿主选择提供指导。与通过条件 include 链连接的源文件相比，通过无条件 include 链包含目标头文件的源文件是更可靠的宿主候选。

已知局限 ​

  • 宏化的 include：形如 #include MACRO_NAME 的 include 无法被快速扫描器解析——它们需要宏展开才能确定实际头文件名。这种模式在实际项目中相对少见；受影响的文件在精确编译期间会被正确处理。
  • 条件编译的精确性：所有条件分支中的 include 都会被记录，使得 include 图比实际更大。这对宿主查找是安全的（不会遗漏），但可能导致关联性判断过于宽泛。
  • 大小写敏感性：在大小写不敏感的文件系统（macOS、Windows）上，如果 include 的大小写与文件名不一致，解析可能失败。
  • Framework 搜索路径：尚未支持 macOS 的 Framework 目录（-F、-iframework）；形如 <Foo/Bar.h> 的 Framework include 无法被正确解析。
