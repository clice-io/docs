重构 ​

概述 ​

clice refactor 根据持久化索引改写项目的源代码，clice query 读取的也是同一份索引。整个过程不做编译，因此在大型源码树上做一次重构，耗时与一次查询相当。目前唯一的重构是 rename；编辑器里的重命名走的也是同一个引擎。

用法：clice refactor rename (<locator> <new-name> | --spec <file>) [--workspace <dir>] [--configuration <tag>] [--dry-run] [--fresh]

重命名 ​

符号由一个定位串（locator）指明，写法与 clice query 接受的相同：可以是一字不差、大小写也一致的名称，也可以是 clice query 某个答案所带的 symbol，或者一个位置 file:line[:column]。和编辑器的光标一样，位置落在模板中依赖于模板参数的名称上时，重命名的是各个实例化把该名称解析到的符号；这些实例化把它解析到分属不同重命名的符号，或者没有任何实例化被索引时，会拒绝重命名。近似匹配或模式不足以作为改写整个项目的依据。同一作用域中的几个重载共用一个名称时，用这个名称会把它们全部重命名；用其中某一个的 symbol 则只重命名那一个。其他几个不同的符号叫同一个名字时，会把它们作为 candidates 列出。

重命名会改动索引关联到该符号的每一处声明、定义和引用，以及必须与它保持同名的那些符号：

  • 类的构造函数和析构函数——重命名构造函数也会重命名它所属的类；
  • 模板的显式特化和偏特化，以及类模板的推导指引（deduction guides）；
  • 基类和派生类中与该虚函数构成覆盖关系的函数。

在模板中，依赖于模板参数的名称（value.print()、T::type）在索引保存的实例化把它解析到该符号时会被重命名；没有任何实例化被索引时，它会被列为不予改动的位置。如果一个实例化把它解析到该符号，另一个实例化却把它解析到另一个同名符号，该名称既不能改，也不能保持原样：重命名就此停止，除非一份重命名清单给两者指定了同一个新名称。如果一次调用的各个重载由模板自身的名称查找就能找到（compute(value)），那么只要这些重载全都在重命名之列，无论是否实例化过，这次调用都会被重命名。

运算符、转换函数、用户定义字面量、在系统头文件中声明的符号，以及每一处声明都由宏写出的符号，都无法重命名。新名称必须是标识符，且既不是 C 的关键字，也不是 C++ 的关键字；使用为实现保留的名称（__x、_X，以及全局作用域中的 _x）会产生警告。

宏 ​

宏名在每个能看到它的翻译单元中都是同一个名称，因此重命名一个宏，会把它彼此关联的各个定义一起重命名：定义或使用它的文件中它的每一个 #define（#if 的每个分支、#undef 之后的重新定义），以及它在别处的使用所解析到的定义，例如在另一组定义下编译的头文件，又如某个宏体写到另一个宏，而每个文件都各自为它定义了那个宏（DEBUG_TYPE 与 LLVM_DEBUG）。另一个库中的同名宏保持不变。重命名会改动它的使用（无论是直接写出，还是作为另一个宏的实参）、检测它的 #ifdef、#ifndef 和 defined、它的 #undef、展开后会写出它的其他宏的宏体；在定义或使用它的文件中，还会改动没有任何定义能够到达、却写有它名字的指令：保护默认定义或头文件的 #ifndef，以及构建排除在外的分支中的 #define。

由编译命令或编译器定义的宏（-DNAME、__GNUC__），以及由系统头文件定义的宏，都无法重命名；在重命名要改动的某处使用上，被某个翻译单元的命令覆盖的宏也无法重命名。项目中的任何符号、宏或 #ifdef 已经写出的名称，无论处于哪个作用域，都不能用作宏的新名称：宏会把它们替换掉。defined 不能用作宏名。

批量重命名 ​

--spec <file> 在一次运行中完成清单文件列出的全部重命名：索引只读一次，因此横跨数百个名称的术语清理，代价与一次重命名相当；索引也只在结束后更新一次，而不是在每两次重命名之间各更新一次。- 表示从 stdin 读取清单。每行的格式是 <locator> => <new name>；空行和以 // 开头的行会被跳过。某一行的定位串匹配到多个符号时，这一行本身就算出错，因此清单最好照着 clice query 每个答案所带的 symbol 来写：

// row → variant, flavor → kind
#645572aaecc8aada => VariantHash
::clice::index::RowSource => IndexSource
JoinFlavor => JoinKind

清单中的重命名同时生效，每个定位串指明的都是任何重命名发生之前索引中的符号：A => B 与 B => C 并存时，原来的 B 会被重命名为 C；两个名称也可以互换。每个新名称都要与整份清单执行之后留下的名称做比对——被另一行改掉名字的符号不再与它冲突，而两行把同一作用域中的符号改成同一个名称则会冲突。某个 Token 同时指向两个被重命名的符号时（例如模板中一次在两个重载之间悬而未决的调用），两者改成同一个名称时它会被改动，名称不同时则会阻止整份清单。某一行要重命名的符号已由前面某一行重命名时，给出的新名称相同则只规划一次，不同则算作冲突。

清单要么全部生效，要么全不生效：某一行没有指明任何符号、任何一行出现冲突，或存在过期文件，都会阻止整份清单，什么也不会写入。若是某一行没有指明符号或出现冲突，改好清单再运行一次即可：由于什么都没有写入，索引仍与磁盘一致。若是存在过期文件，则要先重新建立索引，--fresh 会完成这一步。

答案 ​

答案与查询的一样，是一个 JSON 对象 {"result": ..., "stale": [...]}，单个重命名和一份清单的答案格式相同：

  • renames 为每个请求的重命名给出一项，包括它在清单中的 line、原样照录的 locator、它找到的符号（name、kind、symbol）、它的 newName，以及它改动了多少个 Token（edits）。error 说明该定位串为何没有指明可重命名的符号，匹配到多个符号时附上 candidates。它的 warnings 不会阻止重命名：新名称与同一作用域中的函数构成重载，或是为实现保留的名称；构建中有些翻译单元尚未建立索引，它们写到的名称不会被重命名。它的 conflicts 会阻止这一重命名：新名称已在同一作用域中声明、是一个宏、在重命名宏时与项目中的任一符号或 #ifdef 同名、是同一函数的参数名或标签名、是基类或派生类的成员名、是被重命名成员所属的类名，或是被重命名类的成员名；它改动的某个 Token 在另一个实例化中或另一种构建配置下还指向另一个同名符号；重命名会改动项目之外的文件；两个命名空间会合并成一个；前面某一行已把该符号重命名为另一个名称；它改动的某个 Token 同时指向另一个符号，而另一行要把那个符号改成另一个名称。
  • files 列出每个文件中被替换的 Token，附带行号和以字节计的列号（两者均从 1 开始），以及每个 Token 换下的 name 和换上的 newName。
  • unconfirmed 列出索引关联到某个旧名称 name、但这些重命名不予改动的位置，因为没有哪处所写代码能说明它们指的是什么：#define 的宏体（它在另一次展开中会指向别的东西）、展开后写出该名称的宏或用 ## 拼接而成的宏名、模板中没有任何已索引的实例化将其解析到该符号的名称、模板中可能选中另一个同名重载的调用，以及对宏而言，在既不定义也不使用该宏的文件中、没有任何定义能够到达却写有它名字的指令。构建之前请先读一遍。
  • conflicts 会让所有重命名一起停止：某个 Token 会被其中两个重命名改成不同的名称，或者某个文件无法改写。
  • stale 列出建立索引之后文本又改动过的文件，范围是这些重命名要改动的文件，以及写有某个旧名称或新名称的文件。它们同样会阻止重命名；--fresh 会先为它们重新建立索引。

重命名已写入，或在 --dry-run 下已生成计划时，退出码为 0；被错误、冲突或过期文件阻止时，退出码为 1。选项或清单无法解析时，答案是 {"error": "..."}（清单的错误会指出出错的行），退出码为 1；参数本身无法解析时退出码为 2。

写入 ​

不加 --dry-run 时，命令在所有新文本都算好之后才写入文件：只要有一个文件的文本在计划生成之后发生了变化，整个重命名就会在写入任何内容之前停止。每个文件都原地改写，保留原有的字节序标记（BOM）、换行符和权限；某个文件写不进去时（只读，或磁盘已满），重命名就停在那里，错误信息会列出已经改写过的文件。

命令只编辑项目：隐藏目录、缓存目录和构建目录（含有 CMakeCache.txt 或 build.ninja 的目录）都被排除在外；索引定位到的编辑可能落在任何后缀名的文件中。重命名只读取索引、它要改动的文件，以及建立索引之后改动过的文件，从不读取项目的其余部分：索引没有关联到任何符号的内容既不会被重命名，也不会被列出，例如 #if 排除掉的代码、从未被展开的 #define 的宏体、构建中没有任何翻译单元编译或包含的文件。重命名之后，请在项目中搜索一遍旧名称。

命令读的是磁盘，看不到编辑器中尚未保存的缓冲区。请先保存，或直接在编辑器里重命名。

在编辑器中 ​

编辑器里的重命名会选中光标处的名称，或说明该处的符号为什么无法重命名。它读取已打开的缓冲区而不是磁盘，返回的编辑带有这些缓冲区的版本号。遇到冲突或过期文件时，返回一个列出它们的错误；警告和不予改动的位置会显示在一条消息中。

有歧义的名称 ​

多个符号同名时，需要通过定位信息选定其中一个，否则不会执行任何重命名。

支持

指定有歧义的符号名称

若输入的名称对应两个符号，会列出这两个符号，使用带作用域的名称或候选项的 symbol 即可选定其中一个

名称有歧义时，不会执行任何重命名。每个候选项都带有一个 symbol，可将其原样传回。

批量重命名 ​

一次运行即可规划一组重命名操作并将更改写入文件。

支持

一次完成一组重命名

在文件中列出要执行的重命名操作，每行一个 <symbol> => <new name>，即可在一次运行中完成全部重命名

每一行的重命名操作都基于同一个索引进行规划，文件只写入一次，所有重命名要么全部完成，要么全部不执行。空行和以 // 开头的行会被跳过。

已知限制 ​

  • 这些检查都是静态的：索引看不到的语义变化——实参依赖查找（argument-dependent lookup）找到了另一个函数、叫新名称的成员截获了其类内的某处使用、函数内叫新名称的局部变量或模板参数与被重命名的符号冲突或将其遮蔽、某个重载无法与重命名后的函数共存——都发现不了。重命名之后请构建一次。
  • 读取项目中某个宏的系统头文件（例如读取 NOMINMAX 的 windows.h）只有在某个已建立索引的翻译单元包含它时，才会阻止这个宏的重命名；被 # 转成字符串的宏名保留原来的写法。宏的新名称只会与名称搜索能找到的符号、以及被改动文件中写到的名称比对：另一个文件中同名的局部变量或参数不会被发现。
  • 编辑器里的重命名只通过为该文件提供服务的那个项目的索引来编辑；同一编辑器中打开的另一个项目里对该符号的使用保持不变。
