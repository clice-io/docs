The Vision ​

xclang's goal is to give clang what rustup, cross-rs and cargo-zigbuild give Rust: one compiler for every target. The common targets ship in every host archive, vendor SDKs that cannot be redistributed are fetched from the vendor by the user, and C++ runtimes can be built from source on demand (what is xclang?, cross-compiling). Additional targets beyond the bundled set will be published as separate target archives fetched when a build needs them. Every target follows the hermeticity rule: a program depends at run time only on the OS libraries that cannot be redistributed, and links everything else statically.

Targets ​

A target's tier describes how CI tests it (targets and hosts): Tier 1 runs tests natively on a GitHub-hosted runner (including x86 binaries on x86_64 Windows and WebAssembly binaries under wasmtime), Tier 2 runs tests under emulation or virtualization, and Tier 3 compiles and links without running. A Tier 3 target may build its runtimes from source on demand rather than shipping prebuilt archives. "The user (SDK)" means the target requires a vendor SDK fetched by the user under the vendor's license.

  • A newer glibc: x86_64 and aarch64 Linux targets for programs that need features absent from glibc 2.17, such as -static-pie and newer C library interfaces, paired with the same static libc++ and compiler-rt.
  • Other Linux architectures: each uses the oldest glibc version available for its architecture (riscv64 and loongarch64 have no glibc 2.17), with the sanitizers compiler-rt supports on that architecture.
  • WebAssembly: wasm32-wasip2 links with wasm-component-ld bundled in each host archive; C++ exceptions are opt-in.
  • Android: builds against the NDK's sysroot with xclang's static libc++ configured in the NDK's inline ABI namespace (__ndk1).
  • iOS and Apple's other device platforms: their SDKs ship only in full Xcode (which requires an Apple ID to download), and their C++ runtimes will likely be built from source on demand.
  • Windows 7 and XP: the MSVC target linked against the static CRT and YY-Thunks for APIs missing on older Windows versions (mingw-w64 with libc++ cannot target XP; Windows 9x is out of scope).
  • msvcrt: xclang's MinGW targets use UCRT (Windows 10 and later); a MinGW variant targeting the legacy msvcrt.dll is not planned.
  • Emscripten: emsdk provides its own complete toolchain, so Emscripten is not an xclang target.

The xclang Command ​

itemstatus
Target archives and a release index, for xclang target addPlanned
Fetched targets in the CMake package and the Bazel modulePlanned

xclang target add is built to unpack a per-target archive of the same release into the toolchain directory (sysroot, prebuilt runtimes, compiler-rt, config files and C runtime license notices) using a release manifest that records each target archive's URL, sha256, size, tier and required vendor SDK. Once releases publish target archives, the CMake package and the Bazel module will configure and register fetched targets alongside the bundled ones.

  • Runtimes from source for MSVC targets, and ThinLTO in Bazel: extending runtimes from source to compile libc++ on vcruntime with clang-cl against the fetched Windows SDK; and exposing source-built runtimes in Bazel as cc_library dependencies so Bazel runs ThinLTO backend actions on their bitcode objects.
  • Sanitizers for musl targets: ASan, TSan and LSan intercept C library functions through dlsym, which static musl executables do not have (sanitizers). Supporting them requires a musl target variant that links dynamically against libc.so as Alpine Linux does.
  • libgcc_s.a as a linker script: replacing the empty libgcc_s.a archive in the Linux sysroots with INPUT(-lunwind) so manual Cargo configurations for *-unknown-linux-gnu link without adding -Clink-arg=-l:libunwind.a (without xclang cargo).
  • Not planned: xclang is a compiler toolchain, and editor or linter tools link libclang directly; libc++ is linked statically into each binary rather than shared across dynamic libraries (one libc++ per shared object); conda-forge recipes use conda-forge's dynamically linked compiler packages; and libclang is built for the eight hosts (MinGW on Windows, for clice) rather than the MSVC ABI.

Reproducibility and Supply Chain ​

itemstatus
Relative paths in the debug information of CMake buildsPlanned
Immutable GitHub releasesPlanned
SLSA provenance attestationsPlanned
  • Relative debug paths in CMake: CMake builds currently record the build directory's absolute paths in DWARF and Mach-O debug maps, whereas Bazel builds record paths relative to the execution root (paths in debug information).
  • Immutable GitHub releases and SLSA provenance: preventing a published archive and SHA256SUMS from being replaced together on GitHub (checking a download), and attaching verifiable build provenance attestations tying each release asset to its commit and GitHub Actions workflow run.

Following LLVM ​

itemstatus
LLVM 24.x, and every 23.1 release still to come, each as it is releasedPlanned

Each upstream LLVM release is built with the patch series checked against it, dropping patches that upstream has merged.

Open Questions ​

Design choices inside the items above:

  • Android's sysroot: whether xclang sdk fetch downloads only the needed files from Google's NDK or xclang redistributes the sysroot directly.
  • The runtimes of Apple's device platforms: whether to publish prebuilt archives or build them only from source on demand, since Apple's license treats device platform libraries separately from macOS libraries.
  • A glibc newer than 2.17: whether a build selects it with a named config file (--config=) or a distinct target triple spelling.
  • Where fetched targets are stored: inside the toolchain directory only, or also in a user-selected directory.
