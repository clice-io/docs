On this page

PGO ​

xclang's clang and lld are built with profile-guided optimization (PGO) and ThinLTO on all six hosts from a single frontend profile recorded on Linux x64. On C++ benchmarks in 23.1.2.6, xclang compiles as fast as LLVM's own PGO+ThinLTO release builds on Linux and macOS and takes 11 to 22% less time than LLVM's build on Windows x64; in 23.1.2.1, the profile cut C++ compile times by 16 to 34% compared to the same build without PGO.

The Training ​

PGO optimizes the compiler and linker for the code paths exercised during training. In toolchain/pgo/train.ts, an instrumented Linux x64 build of clang, clang-scan-deps and lld runs workloads matching both build systems and language servers:

  • C and C++ compiles: Abseil (-std=c++20) and SQLite (sqlite3.c, shell.c) at -O0 -g and -O2 for x86_64 and aarch64 Linux, plus SQLite with -O2 -flto=thin for both Linux targets and at -O0 -g and -O2 for x86_64-w64-mingw32.
  • Precompiled headers and editor preambles: one shared precompiled header consumed at -O0 -g, -O2 and -fsyntax-only with code completion on absl::, and a preamble extracted from the leading #include block of each Abseil source file, precompiled once per file and used to parse the body and run code completion (std::, absl::) as an editor does.
  • C++20 modules and P1689 scanning: libc++'s std and std.compat, magic_enum, Vulkan-Hpp (vulkan.cppm and vulkan_video.cppm on x86_64), a wrapped nlohmann/json module, a multi-partition geometry module (shapes, detail, algorithms), and their importers at -std=c++23. At -O2, modules build in two phases (--precompile to .pcm, then .pcm to .o); at -O0 -g, in one phase with reduced module files (-fmodules-reduced-bmi -fmodule-output=). clang-scan-deps -format=p1689 scans individual compile commands (as CMake runs it) and a whole compile_commands.json database for Abseil.
  • Code completion: -fsyntax-only -Xclang -code-completion-at=... across Abseil sources, PCH users, preambles and module importers (std::, nlohmann::, magic_enum::, geometry::, vk::, j.).
  • Linking: ELF links (at -O0 -g, -O2, and -O2 -flto=thin for x86_64 and aarch64 Linux, plus the module programs) and COFF links (x86_64-w64-mingw32 SQLite at -O0 -g and -O2) through lld.

About 1,700 runs in 23 minutes produce one merged profile per release, published as xclang-<version>.profdata (releases).

The training corpus does not currently include Objective-C, clang-cl and MSVC-mode parsing, Mach-O links (ld64.lld), aarch64 COFF links, Windows- or macOS-only host code paths, sanitizer passes, or libclang libraries that clang itself does not call (clang-tidy checks, clangIndex, clangIncludeCleaner). Widening the training corpus to cover those is planned and happens between releases.

One Profile for Every Host ​

clang supports two PGO instrumentation modes, which determine whether a profile recorded on one host can optimize another:

  • IR instrumentation (-fprofile-generate) instruments LLVM IR after early optimization passes and hashes each function's control-flow graph at that point. Because early passes consult target cost models, the same source function can produce different control-flow graphs on x86_64 and arm64, so a profile recorded on one architecture does not match the other.
  • Frontend instrumentation (-fprofile-instr-generate, LLVM's LLVM_BUILD_INSTRUMENTED=Frontend) instruments the clang AST and hashes each function from its source structure. The same source produces the same hash on every target.

xclang uses frontend instrumentation. In experiments before 23.1.2.1, a profile recorded on Linux x64 matched all but 0 or 1 of 113,000 functions on each of the six hosts and gave compile times within runner noise of per-host IR profiles merged from all six hosts (compile time of Abseil / LLVM's Sema relative to no PGO, median of five runners):

Training therefore runs once on a single Linux x64 runner, and its profile optimizes all six host toolchains and libclang archives without per-host instrumented builds or emulation.

The Remapping File ​

Frontend profiles look up each function by its mangled name, and fixed-width and pointer-sized integer types mangle differently across LP64 and LLP64/Darwin ABIs: size_t and uint64_t are unsigned long (m) on Linux but unsigned long long (y) on Windows (and uint64_t is unsigned long long on macOS), while int64_t is long (l) on Linux and long long (x) on Windows and macOS. Without remapping, functions taking size_t or uint64_t have different mangled names on Windows and macOS than in the Linux profile and receive no profile counts.

toolchain/pgo/remap.txt maps type m y and type l x via -fprofile-remapping-file. In the same pre-23.1.2.1 experiments, adding the remapping file improved the Abseil / Sema compile-time ratios on macOS arm64 from 0.896 / 0.923 to 0.794 / 0.845 and on Windows x64 from 0.787 / 0.824 to 0.772 / 0.829.

Two small groups of functions are not matched by LLVM's remapper:

  • On Windows, 230 functions with integer-literal template arguments of those types (1.8% of total counts).
  • Functions with internal linkage: 122 on Windows and 39 on macOS (0.06% and 0.02% of total counts), because frontend profile keys for static functions have the form <file>:<mangled> and the remapper does not strip the <file>: prefix before parsing the mangled name.

What It Buys ​

bench.yml (tests/bench/bench.ts) measures native compile times on runners of each host using code that is not in the training corpus:

  • ten of fmt's tests (template-heavy C++20);
  • the C source files of lua;
  • precompiling libc++'s std module.

Each workload is compiled at -fsyntax-only, -O0 -g and -O2, one file at a time. Rounds interleave the compilers in rotating order on the same runner, taking the median across rounds on each machine and then the median of each machine's ratio to the reference across runners. Differences of a few percent are within runner noise.

The reference compiler is LLVM's official release build of the same version: built with PGO and ThinLTO on Linux and macOS (plus BOLT on Linux x64; BOLT for xclang's Linux hosts is in research), and with PGO without LTO on Windows. Because LLVM publishes no x86_64 macOS binary, xclang itself is the reference on x86_64 macOS.

Summary of the 23.1.2.6 measurements:

  • Linux and macOS: on C++, xclang matches LLVM's PGO+ThinLTO builds; on lua's small C files it takes up to 17% longer. On Linux x64, where LLVM's binary is also BOLT-optimized, xclang takes up to 7% longer on C++ and 12% longer on C.
  • Windows: compared to LLVM's MSVC-built clang (PGO without LTO), xclang's MinGW-built clang (PGO and ThinLTO) takes 11 to 22% less time on C++ on x64 and 5 to 11% less on arm64.
  • Windows launcher overhead: lua's C files each compile in a few dozen milliseconds, so spawning clang++.exe before llvm.exe adds up to 12% on x64 and 25% on arm64 compared to running llvm.exe clang++ directly; on C++ files, the process-start cost is negligible (the launchers).
  • Apple's clang: takes 17 to 29% more time than xclang on fmt across both macOS architectures, and between 25% less and 5% more on lua.
